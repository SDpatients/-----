## P0（阻塞性）

### 1. 修复订单状态值代码与数据库不一致

#### 修复原因

状态值是状态机运转的核心依据。代码与数据库定义不一致会导致：

- 数据库已取消的订单（status=5）在 Java 代码中被当作其他状态处理
- 供应商拒单写入数据库（status=6）后，代码中用 STATUS_REJECTED=8 永远匹配不到
- 所有依赖状态值的查询、统计、风险预警全部错乱

#### 当前问题

| 状态 | 数据库 Schema | Java 代码常量 |
|---|---|---|
| 已取消 | `5` | `STATUS_CANCELED = 7` |
| 已拒单 | `6` | `STATUS_REJECTED = 8` |

数据库定义：[purchase_order 表 L738](file:///d:\.我的项目\供应商协同\database\mysql\supplier_collaboration_full_schema.sql#L738)
代码定义：[PurchaseOrderServiceImpl L35-L39](file:///d:\.我的项目\供应商协同\backend\src\main\java\com\supplier\order\service\impl\PurchaseOrderServiceImpl.java#L35-L39)

#### 目标状态

代码常量与数据库 Schema 完全一致：

| 状态值 | 名称 | 常量名 |
|---|---|---|
| 0 | 待下发 | STATUS_DRAFT |
| 1 | 待确认 | STATUS_PENDING_CONFIRM |
| 2 | 已确认 | STATUS_CONFIRMED |
| 3 | 部分发货 | STATUS_PARTIAL_SHIPPED |
| 4 | 已完成 | STATUS_COMPLETED |
| 5 | 已取消 | STATUS_CANCELED |
| 6 | 已拒单 | STATUS_REJECTED |

#### 实现方案

1. 修改 `PurchaseOrderServiceImpl` 中的常量值：`STATUS_CANCELED = 5`，`STATUS_REJECTED = 6`
2. 补充缺失的状态常量：`STATUS_PARTIAL_SHIPPED = 3`，`STATUS_COMPLETED = 4`
3. 建议将状态常量提升到独立的枚举类 `com.supplier.order.enums.OrderStatusEnum`，避免硬编码散落
4. 全局搜索所有引用 `7` 和 `8` 作为订单状态的地方一并修正

### 2. 补全收货记录、质量检验、订单变更的供应商隔离

#### 修复原因

规范明确要求"供应商用户只能访问自身 supplier_id 数据"。如果这三个模块缺失隔离：

- 供应商 A 登录后可查看供应商 B 的收货记录
- 供应商 A 可查看供应商 B 的质检报告（含不合格原因、处理方式等敏感信息）
- 供应商 A 可查看供应商 B 的订单变更记录（含价格、数量变更等商业机密）

这属于数据越权漏洞，必须在 P0 修复。

#### 当前问题

| 模块 | Service 类 | 是否有隔离 |
|---|---|---|
| 采购订单 | PurchaseOrderServiceImpl | 有 `resolveSupplierId()` + `getOrderWithDataScope()` |
| ASN | DeliveryNoticeServiceImpl | 有 `resolveSupplierId()` + `getWithScope()` |
| 对账 | ReconciliationServiceImpl | 有 `resolveSupplierId()` + `getWithScope()` |
| 收货记录 | ReceiptRecordServiceImpl | **无** -- 仅有 `getById()` |
| 质量检验 | QualityInspectionServiceImpl | **无** -- 仅有 `getById()` |
| 订单变更 | OrderChangeServiceImpl | **无** -- 仅有 `getById()` |

#### 目标状态

所有涉及供应商数据的查询/详情/操作接口，供应商用户登录后强制限定 `supplier_id`。

#### 实现方案

参照 `PurchaseOrderServiceImpl` 的成熟模式：

```java
// 1. 分页查询时：通过 resolveSupplierId 强制限定
private Long resolveSupplierId(Long querySupplierId) {
    if (!SecurityUtils.isSupplierUser()) {
        return querySupplierId;
    }
    Long supplierId = SecurityUtils.getSupplierId();
    if (supplierId == null || (querySupplierId != null && !supplierId.equals(querySupplierId))) {
        throw BusinessException.of(ResultCode.DATA_FORBIDDEN);
    }
    return supplierId;
}

// 2. 详情查询时：校验数据归属
private XxxEntity getWithScope(Long id) {
    XxxEntity entity = mapper.selectById(id);
    if (entity == null) {
        throw BusinessException.of(ResultCode.NOT_FOUND);
    }
    if (SecurityUtils.isSupplierUser() && !entity.getSupplierId().equals(SecurityUtils.getSupplierId())) {
        throw BusinessException.of(ResultCode.DATA_FORBIDDEN);
    }
    return entity;
}
```

需修改的文件：
- `ReceiptRecordServiceImpl` -- 实体需提前确认 `supplier_id` 字段存在
- `QualityInspectionServiceImpl` -- 实体已有 `supplierId` 字段
- `OrderChangeServiceImpl` -- 需通过关联 `purchase_order` 表的 `supplier_id` 做间接校验

## P1（核心缺失）

### 3. 在所有核心业务操作中集成领域事件发布

#### 修复原因

领域事件是消息通知、ES 索引同步、ERP 回传、审计追踪的**唯一触发源**。当前：

- `DomainEventPublisher` / `RabbitDomainEventPublisher` 已实现但零调用
- `MessageNoticeService` 在 Service 层直接同步调用，违反"先落库后发消息"原则
- 未来引入 ES 同步、ERP 回调等需求时，只能到处 hardcode，无法扩展

#### 当前问题

| 业务操作 | 所在方法 | 当前做法 | 问题 |
|---|---|---|---|
| 订单下发 | `publish()` | 直接调用 `portalTodoService.create()` + `messageNoticeService.create()` | 同步耦合，长事务风险 |
| ASN 发货 | `ship()` | 无任何通知 | 仓库不知道有货要来 |
| 质检不合格 | `submit()` | 直接调用 `messageNoticeService.create()` | 同步耦合 |
| 对账发送 | `send()` | 直接调用 `portalTodoService.create()` + `messageNoticeService.create()` | 同步耦合 |

#### 目标状态

核心业务操作完成后发布领域事件，消费端负责通知、同步等副作用。事件命名遵循规范：`{domain}.{entity}.{action}`。

| 事件 | 触发点 |
|---|---|
| `order.purchase.published` | 订单下发 |
| `order.purchase.confirmed` | 供应商接单 |
| `order.purchase.rejected` | 供应商拒单 |
| `order.purchase.canceled` | 订单取消 |
| `delivery.asn.created` | ASN 创建 |
| `delivery.asn.shipped` | ASN 发货 |
| `delivery.receipt.confirmed` | 收货确认 |
| `quality.inspection.submitted` | 质检提交（含不合格） |
| `settlement.reconciliation.sent` | 对账单发送 |
| `settlement.reconciliation.confirmed` | 对账确认 |

#### 实现方案

**Step 1**：在各 ServiceImpl 中注入 `DomainEventPublisher`，在事务方法末尾发布事件

```java
// 以 PurchaseOrderServiceImpl.publish() 为例
@Transactional
public void publish(Long id, OrderActionDTO dto) {
    // ... 状态变更逻辑 ...
    writeTrack(order, STATUS_PENDING_CONFIRM, "订单下发");

    // 发布领域事件（替代直接调用通知服务）
    domainEventPublisher.publish("supplier.order", "order.purchase.published",
            DomainEvent.builder()
                .eventType("order.purchase.published")
                .data(Map.of("businessId", order.getId(), "businessNo", order.getOrderNo(),
                             "supplierId", order.getSupplierId()))
                .build());
}
```

**Step 2**：创建事件消费者 `OrderEventConsumer`，统一处理通知、待办、ES 同步等

```java
@RabbitListener(queues = "supplier.order.queue")
public void handleOrderEvent(DomainEvent event) {
    // 根据 eventType 分发：
    // - order.purchase.published → 创建供应商待办 + 站内信
    // - order.purchase.confirmed  → 更新待办状态 + 通知采购员
    // ...
    // 幂等检查：message_event_log 表中 eventId 唯一
}
```

**Step 3**：消费端写入 `message_event_log` 表，记录发布/消费状态

### 4. 建立统一的审计日志切面，在所有状态变更点写入 SysAuditLog

#### 修复原因

`sys_audit_log` 表已建、Service 已写，但零调用。规范要求"登录、审批、导出、删除、关键状态变更必须留痕"，目前全业务流程均无审计日志，无法满足合规与追溯要求。

#### 当前问题

所有状态变更方法均未写入 `sys_audit_log`。以订单下发为例：`writeTrack()` 只写了 `order_track`，没有写 `sys_audit_log`。

#### 目标状态

每次关键动作（含状态变更）自动写入 `sys_audit_log`，包含：
- `trace_id` -- 链路追踪 ID
- `business_type` / `business_id` / `business_no` -- 业务单据标识
- `action_name` -- 动作名称
- `before_status` / `after_status` -- 状态变更前后
- `operate_time` -- 操作时间

#### 实现方案

**方案 A（推荐）：注解 + AOP 切面**

```java
// 1. 定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditLog {
    String module();         // 模块名称，如 "采购订单"
    String businessType();   // 业务类型，如 "purchase_order"
    String action();         // 动作名称，如 "订单下发"
    String businessIdExpr(); // SpEL 表达式获取业务 ID，如 "#id"
    String businessNoExpr(); // SpEL 表达式获取业务单号
}

// 2. 切面实现
@Aspect
@Component
public class AuditLogAspect {
    @AfterReturning("@annotation(auditLog)")
    public void writeLog(JoinPoint joinPoint, AuditLog auditLog) {
        // 解析 SpEL 获取参数值
        // 写入 SysAuditLog（包括 traceId、用户、状态变更前后等）
    }
}

// 3. 使用
@AuditLog(module = "采购订单", businessType = "purchase_order",
          action = "订单下发", businessIdExpr = "#id")
@Transactional
public void publish(Long id, OrderActionDTO dto) { ... }
```

**方案 B（备选）：提取工具方法**

如不想引入 AOP，可在 `SysAuditLogService` 中提供静态便捷方法，在各 Service 中显式调用：

```java
SysAuditLogService.log("purchase_order", order.getId(), order.getOrderNo(),
    "订单下发", beforeStatus, afterStatus);
```

**覆盖范围**：

| 模块 | 需加审计的动作 |
|---|---|
| 供应商准入 | 审核通过、审核拒绝、暂停、拉黑 |
| 采购订单 | 下发、接单、拒单、取消、变更审批 |
| ASN | 发货、到达确认 |
| 收货 | 确认收货、拒收 |
| 质检 | 提交检验、处理 |
| 对账 | 发送、确认、有异议 |

### 5. 为 DeliveryNotice / QualityInspection / Reconciliation / ReceiptRecord 补充状态轨迹记录

#### 修复原因

规范要求"每次状态变更写入轨迹表"。目前仅采购订单写了 `order_track`。缺少轨迹意味着：

- 无法追溯"谁在什么时间把 ASN 从草稿变为已提交"
- 对账争议时无法还原"供应商何时确认、确认金额多少"
- 质检结果无法追溯"谁检验、何时检验"

#### 当前问题

| 模块 | 轨迹表 | 是否写入 |
|---|---|---|
| 采购订单 | order_track | 是 |
| ASN | **无** | 否 |
| 质检 | **无** | 否 |
| 对账 | **无** | 否 |
| 收货 | **无** | 否 |
| 供应商 | **无** | 否 |

#### 目标状态

参照 `OrderTrack` 模式，为核心单据补充轨迹表或在现有表中写入轨迹。

#### 实现方案

**方案 A：为每个模块建独立的轨迹表**

参照 `order_track` 的字段模式：

```sql
CREATE TABLE delivery_track (
    id BIGINT NOT NULL AUTO_INCREMENT,
    notice_id BIGINT NOT NULL COMMENT 'ASN ID',
    track_status TINYINT NOT NULL COMMENT '轨迹状态',
    track_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '轨迹时间',
    track_remark VARCHAR(500) COMMENT '轨迹说明',
    operator BIGINT COMMENT '操作人',
    operator_name VARCHAR(50) COMMENT '操作人姓名',
    -- 公共字段...
    PRIMARY KEY (id),
    KEY idx_notice_time (notice_id, track_time)
) COMMENT='ASN 状态轨迹表';
```

**方案 B：使用通用轨迹表**

```sql
CREATE TABLE biz_status_track (
    id BIGINT NOT NULL AUTO_INCREMENT,
    business_type VARCHAR(50) NOT NULL COMMENT '业务类型(delivery_notice/quality_inspection/reconciliation)',
    business_id BIGINT NOT NULL COMMENT '业务 ID',
    before_status TINYINT COMMENT '变更前状态',
    after_status TINYINT COMMENT '变更后状态',
    track_remark VARCHAR(500) COMMENT '轨迹说明',
    operator BIGINT COMMENT '操作人',
    operator_name VARCHAR(50) COMMENT '操作人姓名',
    operate_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '操作时间',
    -- 公共字段...
    PRIMARY KEY (id),
    KEY idx_business (business_type, business_id),
    KEY idx_operator_time (operator, operate_time)
) COMMENT='通用业务状态轨迹表';
```

**推荐方案 B**：减少表数量，统一查询方式，且与 `sys_audit_log` 互补（轨迹表存业务上下文，审计表存安全上下文）。

```java
// ReconciliationServiceImpl.send()
```

### 6. 实现 ASN 数量不超过可发数量的校验

#### 修复原因

规范要求"ASN 数量不得超过可发数量"。当前 `DeliveryNoticeServiceImpl.create()` 未校验，可能导致供应商超量发货，收货环节产生混乱。

#### 当前问题

```java
// DeliveryNoticeServiceImpl.create() -- 当前实现
@Transactional
public Long create(DeliveryNoticeCreateDTO dto) {
    // 仅校验了单号唯一性
    // 未校验：通知数量 vs 订单可发数量
    // 未校验：订单状态是否允许发货
    // 未校验：supplierId 与订单 supplierId 是否一致
    ...
}
```

#### 目标状态

ASN 创建时：

1. 校验关联订单存在且状态允许发货（已确认/部分发货）
2. 校验 ASN 明细数量 + 已发货数量 ≤ 订单数量
3. 校验 ASN 的 supplierId 与订单 supplierId 一致

#### 实现方案

```java
@Transactional
public Long create(DeliveryNoticeCreateDTO dto) {
    // 1. 校验订单
    PurchaseOrder order = purchaseOrderMapper.selectById(dto.getOrderId());
    if (order == null) {
        throw BusinessException.of(ResultCode.NOT_FOUND.getCode(), "关联订单不存在");
    }
    if (!Integer.valueOf(2).equals(order.getOrderStatus())
        && !Integer.valueOf(3).equals(order.getOrderStatus())) {
        throw BusinessException.of(ResultCode.STATUS_NOT_ALLOWED.getCode(), "订单状态不允许发货");
    }

    // 2. 校验供应商
    if (!order.getSupplierId().equals(dto.getSupplierId())) {
        throw BusinessException.of(ResultCode.DATA_FORBIDDEN.getCode(), "供应商与订单不匹配");
    }

    // 3. 校验数量
    BigDecimal alreadyDelivered = deliveryDetailMapper.sumDeliveredByOrderDetail(dto.getOrderDetailId());
    BigDecimal availableQty = orderDetail.getQuantity().subtract(alreadyDelivered);
    if (dto.getPlanQty().compareTo(availableQty) > 0) {
        throw BusinessException.of(ResultCode.PARAM_ERROR.getCode(),
            "送货数量超过可发数量，可发：" + availableQty);
    }

    // ... 创建 ASN ...
}
```

### 8. 实现 JWT 黑名单机制

#### 修复原因

规范要求"登出后应记录黑名单或通过 token version 失效"。当前：

- 用户登出后 JWT 仍然有效，直到自然过期
- 管理员禁用用户后，已签发的 token 仍可继续使用
- `sys_user.token_version` 字段已定义但未使用

#### 当前问题

[SecurityConfig](file:///d:\.我的项目\供应商协同\backend\src\main\java\com\supplier\security\config\SecurityConfig.java) 中的 JWT Filter 仅做签名校验和过期校验，没有黑名单检查。

#### 目标状态

1. 用户登出时，将 token 的 jti 写入 Redis 黑名单
2. JWT Filter 校验时，先检查 jti 是否在黑名单中
3. 管理员禁用/锁定用户时，递增 `token_version`，使该用户所有旧 token 失效

#### 实现方案

```java
// JwtAuthenticationFilter 中增加黑名单检查
@Override
protected void doFilterInternal(...) {
    String token = resolveToken(request);
    if (token != null) {
        String jti = jwtUtil.getJtiFromToken(token);
        // 1. 检查 Redis 黑名单
        if (redisTemplate.hasKey("auth:blacklist:" + jti)) {
            // token 已被登出
            response.sendError(401, "令牌已失效");
            return;
        }
        // 2. 检查 token_version
        Long userId = jwtUtil.getUserIdFromToken(token);
        Integer tokenVersion = jwtUtil.getTokenVersionFromToken(token);
        Integer currentVersion = redisTemplate.opsForValue()
            .get("auth:token_version:" + userId);
        if (currentVersion != null && !currentVersion.equals(tokenVersion)) {
            response.sendError(401, "令牌版本已变更，请重新登录");
            return;
        }
        // ... 现有逻辑 ...
    }
}

// AuthController.logout()
@PostMapping("/logout")
public Result<Void> logout() {
    String token = request.getHeader("Authorization").substring(7);
    String jti = jwtUtil.getJtiFromToken(token);
    Date expiration = jwtUtil.getExpirationFromToken(token);
    long ttl = expiration.getTime() - System.currentTimeMillis();
    // 写入 Redis 黑名单，TTL 与 token 剩余有效时间一致
    redisTemplate.opsForValue().set("auth:blacklist:" + jti, "1", ttl, TimeUnit.MILLISECONDS);
    return Result.ok();
}
```

### 9. 实现幂等性机制

#### 修复原因

规范要求"外部推送、消息消费、表单重复提交、导入导出必须具备幂等设计"。`sys_idempotent_record` 表已建但零使用。缺失幂等机制会导致：

- 用户重复点击"提交"按钮产生重复单据
- 消息重复消费导致重复通知
- ERP 重复推送同一订单导致数据重复

#### 目标状态

关键接口支持幂等 Token 机制或业务唯一键去重。

#### 实现方案

**方案 A：幂等 Token（适用于表单提交）**

```java
// 1. 前端在打开表单时从后端获取 token
@GetMapping("/idempotent-token")
public Result<String> getToken() {
    String token = UUID.randomUUID().toString();
    redisTemplate.opsForValue().set("idempotent:" + token, "1", 5, TimeUnit.MINUTES);
    return Result.ok(token);
}

// 2. 自定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    String keyExpr(); // SpEL 表达式
}

// 3. 切面实现
@Around("@annotation(idempotent)")
public Object around(ProceedingJoinPoint joinPoint, Idempotent idempotent) {
    String key = parseSpEL(idempotent.keyExpr(), joinPoint);
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent("idempotent:" + key, "1", 5, TimeUnit.MINUTES);
    if (!success) {
        throw BusinessException.of(ResultCode.DUPLICATE_SUBMIT);
    }
    try {
        return joinPoint.proceed();
    } catch (Throwable e) {
        redisTemplate.delete("idempotent:" + key); // 失败则释放
        throw e;
    }
}

// 4. 使用
@Idempotent(keyExpr = "'order_create_' + #dto.orderNo")
@PostMapping
public Result<Long> create(@RequestBody PurchaseOrderCreateDTO dto) { ... }
```

**方案 B：业务唯一键 + DB 唯一约束（适用于外部推送/消息消费）**

```java
    idempotentRecordMapper.insert(record);

}
```

```java
@Component
public class RedisLockUtil {
    public boolean tryLock(String key, long timeoutMs) {
        return Boolean.TRUE.equals(redisTemplate.opsForValue()
                .setIfAbsent("lock:" + key, "1", timeoutMs, TimeUnit.MILLISECONDS));
    }
    public void unlock(String key) {
        redisTemplate.delete("lock:" + key);
    }
}
```
