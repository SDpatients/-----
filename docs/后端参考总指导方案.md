# 供应商协同系统后端参考总指导方案

## 1. 文档定位

本文档基于《供应商协同系统架构详解》和《供应商协同系统规则规范》整理，目的是为后端研发提供一份可直接落地的总指导方案。它不替代详细设计，而是统一后端的技术边界、模块划分、分层方式、接口风格、数据规范、安全要求、消息机制、文件存储、测试验收与交付标准，保证后续新增模块在同一套工程约束下演进。

## 2. 建设目标

### 2.1 业务目标

- 支撑采购方与供应商之间的寻源、订单、交付、质量、结算、通知与集成协同闭环
- 实现内部用户与外部供应商的强隔离访问与最小权限控制
- 保证关键单据、状态流转、审批动作、消息投递、附件上传全程可追溯
- 为 ERP、WMS、MES、财务系统、OCR、短信、邮件、企微等外部系统提供稳定集成能力

### 2.2 技术目标

- 后端采用 Spring Boot 3 作为统一应用基础，按业务域模块化组织代码
- 接口统一遵循 REST 风格、版本化路径、统一响应与统一错误码
- 数据层遵循 MySQL 主存储、Redis 缓存、RabbitMQ 异步解耦、MongoDB 日志与文档、MinIO 文件、Elasticsearch 检索的分层策略
- 所有核心流程具备状态机、幂等、审计、限流、告警与回滚能力

## 3. 总体后端架构

### 3.1 架构原则

- 先模块化单体，后按领域逐步拆分服务
- 业务逻辑放在 Service 层，Controller 只负责参数接收与结果返回
- 核心单据默认逻辑删除，禁止随意物理删除
- 所有关键状态变更必须走专用方法，不允许直接更新状态字段
- 外部系统交互、消息消费、导入导出、重复提交必须支持幂等

### 3.2 推荐技术栈

| 层级 | 建议技术 |
|---|---|
| Web 框架 | Spring Boot 3 |
| 安全认证 | Spring Security + JWT + RBAC |
| ORM | MyBatis-Plus |
| 接口文档 | Knife4j / OpenAPI |
| 缓存 | Redis |
| 消息队列 | RabbitMQ |
| 文档与日志 | MongoDB |
| 文件存储 | MinIO |
| 检索 | Elasticsearch |
| 构建 | Maven |
| 容器部署 | Docker Compose |

## 4. 后端模块规划

### 4.1 公共基础模块

公共模块承担所有业务模块都会复用的能力，不允许在各业务模块中重复造轮子。

| 子能力 | 职责 |
|---|---|
| result | 统一响应结构、分页结构、状态码 |
| exception | 业务异常、参数校验异常、全局异常处理 |
| entity | 公共实体字段、逻辑删除、版本号 |
| handler | 审计字段自动填充 |
| config | Redis、MQ、MyBatis 等基础配置 |
| utils | 用户上下文、租户上下文、日期工具、ID 工具 |

### 4.2 安全认证模块

| 子能力 | 职责 |
|---|---|
| AuthController | 登录、登出、当前用户信息 |
| AuthService | 认证、令牌签发、角色权限装配 |
| JwtAuthenticationFilter | 解析 JWT 并构建安全上下文 |
| JwtUtil | 令牌生成、解析、校验 |
| SecurityConfig | 白名单、鉴权规则、过滤器链配置 |
| AuthenticationEntryPointImpl | 未认证与令牌失效统一处理 |

### 4.3 业务域模块

后端业务建议按领域拆分为以下模块：

- sourcing：供应商准入、RFQ、比价、招投标
- order：采购订单同步、下发、确认、交期反馈、变更、风险看板
- logistics：ASN、标签、收货、JIT/VMI
- quality：IQC、NCR、8D、质量申诉
- settlement：三单匹配、对账、发票、付款、扣款
- portal：供应商门户能力与外部用户操作接口
- integration：ERP、WMS、MES、财务、OCR、消息通道等集成适配
- system：用户、角色、菜单、字典、权限、审计、参数等系统能力

## 5. 包结构与代码分层

### 5.1 推荐包结构

```text
com.supplier.{module}/
├── controller
├── service
├── service/impl
├── mapper
├── entity
├── dto
├── vo
├── query
├── enum
├── converter
└── event
```

### 5.2 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| Controller | 参数接收、校验、结果返回 | 写复杂业务逻辑 |
| Service | 事务边界、业务编排、状态流转 | 直接拼接 SQL |
| Mapper | 数据访问 | 写业务判断 |
| Entity | 数据库映射 | 直接暴露给前端 |
| DTO | 请求入参 | 承载数据库注解 |
| VO | 响应出参 | 参与数据库写入 |
| Converter | 对象转换 | 混入业务校验 |

### 5.3 代码组织原则

- 一个模块一个边界，避免跨模块直接访问内部实现
- 公共能力下沉到 common，禁止在业务模块复制工具类
- 与状态、金额、权限相关的逻辑应集中在领域服务中
- 对外接口、消息事件、定时任务应明确归属模块

## 6. 接口设计总要求

### 6.1 路径与方法规范

| 规则 | 示例 |
|---|---|
| 统一前缀 | `/api/v1` |
| 资源名复数 | `/api/v1/purchase-orders` |
| 子资源表达层级 | `/api/v1/purchase-orders/{id}/details` |
| 动作用子路径 | `/api/v1/purchase-orders/{id}/confirm` |
| 查询条件用 Query | `/api/v1/suppliers?status=1&keyword=abc` |

| 方法 | 用途 |
|---|---|
| GET | 查询、详情、导出任务状态 |
| POST | 新增、提交、登录、业务动作 |
| PUT | 全量更新或明确保存 |
| PATCH | 局部更新、状态变更 |
| DELETE | 删除或作废，核心单据优先用动作接口替代 |

### 6.2 统一响应规范

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": "2026-05-21 10:00:00",
  "traceId": "9f7c2a..."
}
```

分页响应应统一返回 records、total、pageNum、pageSize、pages 等字段，前端不得为不同接口编写多套解析逻辑。

### 6.3 错误码与异常

| 范围 | 类型 | 示例 |
|---|---|---|
| 200 | 成功 | 200 操作成功 |
| 400xx | 请求错误 | 参数错误、数据不存在 |
| 401xx | 认证错误 | 未登录、令牌过期 |
| 403xx | 授权错误 | 无权限、数据越权 |
| 409xx | 冲突错误 | 状态不允许、重复提交 |
| 500xx | 系统错误 | 系统异常、外部系统异常 |

异常处理要求：

- 参数校验错误返回字段级提示
- 业务异常返回明确错误码与业务提示
- 外部系统异常应记录接口日志并支持重试或补偿
- 未知异常不得向前端暴露堆栈信息

### 6.4 参数校验与幂等

- 新增接口必须校验必填项、枚举值、金额、数量、时间范围
- 更新接口必须校验 ID，建议校验版本号实现乐观锁
- 批量接口要限制最大条数，避免大包请求拖垮服务
- 外部推送、付款回传、消息消费、导入导出、表单重复提交都必须具备幂等设计

## 7. 数据设计总规范

### 7.1 数据库基础要求

| 项目 | 规范 |
|---|---|
| 数据库版本 | MySQL 8.0+ |
| 字符集 | `utf8mb4` |
| 存储引擎 | InnoDB |
| 主键 | `BIGINT`，字段名固定为 `id` |
| 金额 | `DECIMAL(18,2)` |
| 数量 | `DECIMAL(18,4)` |
| 状态 | `TINYINT` |
| 时间 | `DATETIME` |

### 7.2 表命名与公共字段

- 表名使用小写蛇形命名
- 系统表以 `sys_` 开头，供应商表以 `supplier_` 开头，订单表以 `purchase_` 或 `order_` 开头
- 核心业务表必须包含 `create_time`、`create_by`、`update_time`、`update_by`、`deleted`、`version`
- 强业务单据建议包含 `tenant_id`、`org_id`、`supplier_id`、`status`、`submit_time`、`audit_time`、`close_time`

### 7.3 唯一键与索引

- 主键只承担行标识，业务唯一性必须依赖唯一索引
- 用户、角色、供应商、订单、ASN、对账单、发票等必须建立业务唯一索引
- 高频查询字段、时间范围字段、状态字段、隔离字段必须设计联合索引
- 任意模糊搜索优先走 Elasticsearch，避免在 MySQL 上做低效扫描

### 7.4 状态机与逻辑删除

- 所有核心单据必须定义状态流转表
- 状态字段不能被前端任意传值覆盖
- 核心单据默认逻辑删除，删除前必须检查引用关系
- 删除、作废、关闭均应保留审计轨迹

### 7.5 单号与金额规范

- 单号应包含业务前缀、日期分区和序列号
- 禁止直接使用时间戳拼接作为唯一单号
- 金额计算必须统一舍入规则，项目内保持一致
- 外币单据必须记录币种与汇率

## 8. 安全与权限控制

### 8.1 认证规范

- 统一使用 `Authorization: Bearer {token}` 传递 JWT
- 登录失败需要具备验证码、锁定或限流策略
- Token 应区分短效访问令牌与长效刷新令牌
- 登出后应记录黑名单或通过 token version 失效
- 密码必须使用不可逆哈希存储

### 8.2 授权规范

| 规则 | 说明 |
|---|---|
| 最小权限 | 新角色默认无权限，按需授权 |
| 后端强校验 | 接口必须校验功能权限与数据权限 |
| 供应商隔离 | 供应商用户只能访问自身 `supplier_id` 数据 |
| 敏感字段脱敏 | 银行账号、税号、手机号等按场景脱敏 |
| 导出权限独立 | 导出、下载、批量操作需要单独授权 |

### 8.3 输入与文件安全

- SQL 查询必须使用参数绑定，禁止字符串拼接
- 富文本与用户输入展示前应过滤或转义
- 文件上传必须限制大小、类型、扩展名与 MIME
- 文件下载必须校验业务权限，不暴露真实磁盘路径
- 回调地址、重定向地址必须白名单校验

## 9. 消息与异步机制

### 9.1 事件命名

事件采用 `{domain}.{entity}.{action}` 格式，例如：

- `order.purchase.created`
- `order.purchase.confirmed`
- `delivery.asn.created`
- `quality.ncr.created`
- `settlement.reconciliation.confirmed`

### 9.2 事件消息结构

```json
{
  "eventId": "uuid",
  "eventType": "order.purchase.created",
  "occurredAt": "2026-05-21 10:00:00",
  "source": "supplier-collaboration",
  "traceId": "trace-id",
  "data": {
    "businessId": 1,
    "businessNo": "PO202605210001"
  }
}
```

### 9.3 消费与发布规范

- 先完成本地事务，再发布领域事件
- 消息消费必须支持幂等、重试、死信与人工补偿
- 同一业务单据若存在顺序要求，应按业务 ID 保序处理
- 消息日志、失败次数、堆积数量应纳入监控

## 10. 文件与存储规范

### 10.1 对象存储路径

建议采用如下结构：

```text
{bucket}/{module}/{yyyy}/{MM}/{dd}/{businessNo}/{uuid}.{ext}
```

### 10.2 文件元数据

上传后建议保存以下信息：

- file_name
- file_ext
- file_size
- content_type
- bucket_name
- object_key
- file_hash
- business_type
- business_id

### 10.3 存储策略

- 资质、合同、图纸、发票、报告、标签等文件应按业务桶分类
- 附件下载必须经过权限判断
- 对高频上传下载文件要考虑去重与完整性校验

## 11. 缓存规范

| 场景 | 规则 |
|---|---|
| 字典缓存 | 修改后主动删除缓存 |
| 权限缓存 | 角色变化后清理对应用户缓存 |
| 热点列表 | 允许短 TTL 缓存 |
| 分布式锁 | 必须设置过期时间并校验持有者 |
| 缓存穿透 | 空值短 TTL 或布隆过滤器 |
| 缓存击穿 | 热点 key 加互斥锁或逻辑过期 |

## 12. 可观测性与审计

### 12.1 日志规范

| 日志类型 | 内容 |
|---|---|
| 请求日志 | traceId、用户、IP、方法、路径、耗时、状态码 |
| 业务日志 | 单据号、动作、前状态、后状态、操作人 |
| 错误日志 | traceId、异常类型、堆栈、关键上下文 |
| 集成日志 | 请求地址、请求摘要、响应摘要、耗时、重试次数 |
| 安全日志 | 登录、越权、导出、删除、敏感字段查看 |

### 12.2 审计要求

- 登录、审批、导出、删除、作废、关键状态变更必须留痕
- 外部接口请求响应摘要应可追踪
- 日志中不得输出密码、JWT、银行卡完整号、密钥等敏感信息

### 12.3 监控与告警

- 监控应用 QPS、延迟、错误率、连接池、线程池、JVM 指标
- 监控消息积压、慢 SQL、磁盘不足、外部接口失败率
- 对关键链路配置明确告警阈值与通知渠道

## 13. 事务与状态流转规范

### 13.1 事务要求

- 新增、修改、删除、状态流转必须具备事务边界
- 事务注解放在 public Service 方法上
- 文件上传、外部接口调用、消息发送不应放入长事务
- 本地事务成功后再做副作用处理

### 13.2 状态控制

- 状态变更必须通过专用服务方法执行
- 变更前先校验当前状态与用户权限
- 每次变更都要写轨迹表
- 高并发场景使用乐观锁或行锁防止重复变更

## 14. 典型业务流程落地要求

### 14.1 供应商准入

- 统一信用代码必须唯一
- 资质有效期、黑名单、联系人手机号必须校验
- 审核轨迹必须留存
- 准入状态不得跳跃

### 14.2 采购订单协同

- 订单号唯一
- 供应商只能访问自身订单
- 接单、拒单、交期反馈、变更确认均需记录轨迹
- 关键状态变化要发送消息

### 14.3 ASN 与收货

- ASN 数量不得超过可发数量
- 条码、送货单、箱号、批次号应可追溯
- 收货差异必须记录原因
- 收货后不可随意修改 ASN，必要时通过冲销或调整处理

### 14.4 质量异常与对账

- 不合格数量必须与收货记录一致
- NCR、8D、申诉、扣款要形成闭环
- 对账单冻结后明细不可随意修改
- 发票金额不得超过可开票金额

## 15. 测试与验收标准

### 15.1 测试分层

| 类型 | 覆盖内容 |
|---|---|
| 单元测试 | 工具类、状态机、金额计算、权限判断 |
| 集成测试 | Mapper、Service、消息消费、外部接口适配 |
| API 测试 | 登录、订单、ASN、质检、对账等接口 |
| 前端联调 | 表单校验、权限按钮、关键页面渲染 |
| 冒烟测试 | 登录、接单、发货、收货、质检、对账主链路 |
| 安全测试 | 越权、SQL 注入、XSS、文件上传绕过 |

### 15.2 验收重点

- 内部用户与供应商用户登录后菜单和数据范围正确
- 供应商只能访问自身数据，无法越权查询或操作
- 重复提交与重复消费不会导致状态异常
- 关键流程的日志、审计、消息、附件可追溯
- 导出、下载、删除等敏感操作有权限控制与日志记录

## 16. 交付与运维规范

### 16.1 配置与环境

- dev、test、uat、prod 使用不同配置
- 密码、密钥、令牌不得提交到代码库
- 生产环境必须修改默认账号密码
- 配置变更需记录变更人、时间、原因

### 16.2 发布与回滚

- 构建、测试、数据库变更、发布、回滚都要标准化
- 数据库变更先备份再执行，必要时提供回滚脚本
- 应用发布支持滚动、蓝绿或灰度
- 核心变更要预设镜像、配置、数据库三层回滚方案

### 16.3 备份要求

| 组件 | 备份内容 | 建议 |
|---|---|---|
| MySQL | 全量备份、Binlog | 每日全量 + 实时 Binlog |
| Redis | RDB、AOF | 按重要性开启 AOF |
| MongoDB | dump 或快照 | 每日备份 |
| MinIO | 对象数据与桶策略 | 定期同步备份 |
| Elasticsearch | Snapshot | 定期快照 |

## 17. 开发落地清单

每个新模块上线前，后端至少应确认以下事项：

- 数据表、字段、索引、唯一键符合规范
- Controller、Service、Mapper 分层清晰
- 接口路径、响应结构、错误码统一
- 权限、数据范围、供应商隔离已经落实
- 状态机、幂等、审计、消息机制已经设计
- 文件上传、下载、导出已考虑安全与权限
- 单元测试、接口测试、冒烟测试已经覆盖主流程
- 日志、监控、告警、回滚方案准备完成

## 18. 后续演进建议

- 第一阶段先完成模块化单体，统一规范与主流程闭环
- 第二阶段按订单、质量、结算、门户、集成边界拆分独立服务
- 第三阶段增强多租户、插件化集成、低代码流程、智能预警与数据分析能力

## 19. 总结

这份后端参考总指导方案的核心目标，是让所有后端开发都围绕同一套架构边界和工程规则展开：模块要清晰、接口要统一、数据要可控、权限要严密、消息要可靠、日志要可追溯、发布要可回滚。只要新增功能都遵循本方案，整个供应商协同系统就能保持长期一致性和可演进性。
