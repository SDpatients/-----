# 供应商协同系统规则规范

## 1. 文档定位

本文档定义供应商协同系统在数据库结构、接口设计、后端编码、前端编码、安全权限、消息事件、文件存储、日志审计、部署运维与测试验收方面的统一规范。所有新增模块、表结构、接口与页面应遵循本文档，避免业务实现风格不一致、数据不可追溯、权限绕过和后期维护困难。

## 2. 通用设计原则

| 原则 | 要求 |
|---|---|
| 业务可追溯 | 关键单据必须记录创建、提交、审核、确认、关闭、作废等轨迹 |
| 数据可恢复 | 核心业务表默认逻辑删除，不直接物理删除 |
| 状态可控 | 单据状态必须通过明确状态机流转，禁止任意更新状态字段 |
| 权限后置校验 | 前端控制只用于体验，后端必须完成权限与数据范围校验 |
| 幂等优先 | 外部集成、消息消费、重复提交、导入任务必须可幂等处理 |
| 异常显式 | 业务失败必须返回明确错误码和错误信息，不使用模糊异常 |
| 配置外置 | 密码、密钥、端点、桶名、队列名、限流阈值必须配置化 |
| 最小权限 | 用户、接口账号、数据库账号、对象存储账号均按最小权限授权 |

## 3. 数据库结构规范

### 3.1 数据库基础规则

| 项目 | 规范 |
|---|---|
| 数据库版本 | MySQL 8.0+ |
| 字符集 | `utf8mb4` |
| 排序规则 | `utf8mb4_general_ci`，如需严格排序可按表指定 `utf8mb4_0900_ai_ci` |
| 存储引擎 | InnoDB |
| 时区 | 应用、数据库、容器统一使用 Asia/Shanghai 或统一 UTC 后由前端展示转换 |
| 表名 | 小写蛇形命名，模块前缀 + 业务名，例如 `purchase_order` |
| 字段名 | 小写蛇形命名，语义清晰，避免缩写过度 |
| 主键 | `BIGINT`，字段名固定为 `id` |
| 金额 | `DECIMAL(18,2)`，严禁使用 FLOAT 或 DOUBLE |
| 数量 | 常规数量 `DECIMAL(18,4)`，包装数量可按业务使用 INT |
| 状态 | `TINYINT`，配套字典或枚举说明 |
| 时间 | `DATETIME`，字段名以 `_time` 或 `_date` 结尾 |
| 备注 | 短备注 `VARCHAR(500)`，长文本使用 `TEXT` |

### 3.2 表命名规范

| 类型 | 命名规则 | 示例 |
|---|---|---|
| 系统表 | `sys_` + 名称 | `sys_user`、`sys_role` |
| 供应商表 | `supplier_` + 名称 | `supplier_info` |
| 订单表 | `purchase_` 或 `order_` + 名称 | `purchase_order`、`order_change` |
| 物流表 | `delivery_` 或 `receipt_` + 名称 | `delivery_notice`、`receipt_record` |
| 质量表 | `quality_` 或 `ncr_` + 名称 | `quality_inspection` |
| 财务表 | `reconciliation_`、`invoice`、`payment` | `reconciliation_detail` |
| 关系表 | 主表 + 从表或业务关系 | `sys_user_role` |
| 日志表 | 业务名 + `_log` | `order_status_log` |
| 历史表 | 业务名 + `_history` | `purchase_order_history` |

### 3.3 公共字段规范

核心业务表必须包含以下公共字段：

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `id` | BIGINT | AUTO_INCREMENT 或雪花 ID | 主键 |
| `create_time` | DATETIME | CURRENT_TIMESTAMP | 创建时间 |
| `create_by` | BIGINT | NULL | 创建人用户 ID |
| `update_time` | DATETIME | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |
| `update_by` | BIGINT | NULL | 更新人用户 ID |
| `deleted` | TINYINT | 0 | 逻辑删除，0 未删除，1 已删除 |
| `version` | INT | 0 | 乐观锁版本号 |

强业务单据建议额外包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `tenant_id` | BIGINT | 多租户预留字段 |
| `org_id` | BIGINT | 采购组织、工厂或业务组织 |
| `supplier_id` | BIGINT | 供应商数据隔离字段 |
| `status` | TINYINT | 主状态 |
| `submit_time` | DATETIME | 提交时间 |
| `audit_time` | DATETIME | 审核时间 |
| `close_time` | DATETIME | 关闭时间 |
| `remark` | VARCHAR(500) | 业务备注 |

| 场景 | 类型 | 示例 |
|---|---|---|
| 主键、外键 | BIGINT | `supplier_id BIGINT` |

| 日期 | DATE | `establish_date DATE` |

### 3.6 主键与业务唯一键规范

主键只承担数据库行标识，业务唯一性必须由唯一索引保障。订单号、供应商编码、发票号、角色编码、字典编码等均应建立唯一索引或联合唯一索引。

| 对象 | 唯一键建议 |
|---|---|
| 用户 | `uk_username(username)` |
| 角色 | `uk_role_code(role_code)` |
| 供应商 | `uk_supplier_code(supplier_code)`、`uk_credit_code(credit_code)` |
| 采购订单 | `uk_order_no(order_no)` |
| ASN | `uk_notice_no(notice_no)` |
| 对账单 | `uk_recon_no(recon_no)` |
| 发票 | `uk_invoice_no(invoice_no)`，如存在多税号应使用 `invoice_no + tax_number` |

### 3.7 索引规范

| 场景 | 索引规则 |
|---|---|
| 查询条件 | 高频 where 字段建立普通索引或联合索引 |
| 排序分页 | `WHERE` 条件字段 + `ORDER BY` 字段设计联合索引 |
| 数据隔离 | `supplier_id`、`org_id`、`tenant_id` 必须参与常用联合索引 |
| 状态查询 | 状态字段基数低，建议与业务主字段组合建索引 |
| 时间范围 | 高频列表按 `create_time`、`order_date`、`receipt_time` 建索引 |
| 模糊查询 | 前缀匹配可用 BTree；任意模糊应走 Elasticsearch |
| 关联表 | 关联双方字段分别建索引，必要时建立联合唯一索引 |

联合索引示例：

```sql
KEY idx_supplier_status_time (supplier_id, order_status, order_date),
KEY idx_org_status_create_time (org_id, status, create_time),
UNIQUE KEY uk_user_role (user_id, role_id)
```

### 3.8 外键约束规范

项目建表脚本可不强制使用数据库物理外键，避免高并发写入和跨系统同步时产生强耦合，但必须在应用层保证引用完整性。对关键主从表应遵循以下规则：

| 场景 | 规则 |
|---|---|
| 主从新增 | 先保存主表，再保存明细表，明细必须持有主表 ID |
| 主从删除 | 核心单据禁止物理删除，作废或关闭后保留明细 |
| 明细变更 | 已提交、已审核、已对账的明细不得直接修改 |
| 引用校验 | 创建订单、ASN、收货、对账前必须校验关联对象存在且状态允许 |

### 3.9 状态字段规范

状态值必须枚举化，禁止在代码中散落魔法数字。数据库注释、后端枚举、前端字典三者含义必须一致。

采购订单状态建议：

| 值 | 名称 | 说明 |
|---|---|---|
| 0 | 待下发 | ERP 同步后尚未通知供应商 |
| 1 | 待确认 | 已下发，等待供应商接单 |
| 2 | 已确认 | 供应商已接单并确认交期 |
| 3 | 部分发货 | 已有部分 ASN 或收货 |
| 4 | 已完成 | 全部交付并关闭 |
| 5 | 已取消 | ERP 或采购方取消 |
| 6 | 已拒单 | 供应商拒绝接单 |

ASN 状态建议：

| 值 | 名称 |
|---|---|
| 0 | 草稿 |
| 1 | 已提交 |
| 2 | 在途 |
| 3 | 部分收货 |
| 4 | 已收货 |
| 5 | 已取消 |

对账状态建议：

| 值 | 名称 |
|---|---|
| 0 | 草稿 |
| 1 | 待供应商确认 |
| 2 | 供应商已确认 |
| 3 | 有异议 |
| 4 | 已开票 |
| 5 | 已付款 |
| 6 | 已关闭 |

### 3.10 金额与税务规范

| 规则 | 说明 |
|---|---|
| 价格口径明确 | 字段名区分含税价 `tax_price` 与未税价 `price` |
| 税率保存 | 税率使用 `DECIMAL(10,4)`，例如 13% 保存为 0.1300 |
| 金额冗余 | 单据头可保存汇总金额，但必须由明细计算得出 |
| 舍入规则 | 金额统一按银行家舍入或四舍五入，项目内必须固定一种 |
| 币种字段 | 涉及外币必须保存 `currency` 与 `exchange_rate` |
| 发票约束 | 发票金额不得超过已确认可开票金额 |

### 3.11 单号生成规范

单号应具备业务含义、日期分区和序列号，避免纯自增暴露业务规模。

| 单据 | 前缀 | 示例 |
|---|---|---|
| 采购订单 | PO | `PO202605210001` |
| 订单变更 | PCO | `PCO202605210001` |
| ASN | ASN | `ASN202605210001` |
| 收货单 | GR | `GR202605210001` |
| NCR | NCR | `NCR202605210001` |
| 对账单 | REC | `REC202605210001` |
| 发票登记 | INV | `INV202605210001` |

单号生成必须在并发场景下安全，可使用 Redis 原子递增、数据库序列表或雪花 ID 派生。禁止使用当前时间毫秒直接拼接作为唯一单号。

### 3.12 逻辑删除规范

| 规则 | 说明 |
|---|---|
| 默认查询过滤 | 所有业务查询默认追加 `deleted = 0` |
| 删除前校验 | 被订单、对账、质量单引用的数据不得删除 |
| 删除留痕 | 删除操作必须记录操作人、时间、原因 |
| 唯一键处理 | 逻辑删除表的唯一键需考虑删除后重建问题，可组合 `deleted` 或使用业务归档策略 |

### 3.13 数据迁移规范

| 规则 | 说明 |
|---|---|
| 脚本版本化 | 所有 DDL、DML 变更必须形成版本脚本 |
| 禁止手工改库 | 生产变更必须通过审核脚本执行 |
| 先兼容后清理 | 字段改名、类型变更采用新增字段、双写、迁移、切换、删除旧字段步骤 |
| 大表变更 | 大表加字段、加索引需评估锁表风险，必要时使用在线 DDL |
| 可回滚 | 关键变更必须提供回滚方案或备份方案 |

## 4. API 设计规范

### 4.1 路径规范

| 规则 | 示例 |
|---|---|
| 统一前缀 | `/api/v1` |
| 使用资源名复数 | `/api/v1/purchase-orders` |
| 子资源表达层级 | `/api/v1/purchase-orders/{id}/details` |
| 动作用子路径 | `/api/v1/purchase-orders/{id}/confirm` |
| 查询条件使用 Query | `/api/v1/suppliers?status=1&keyword=abc` |

### 4.2 HTTP 方法规范

| 方法 | 用途 |
|---|---|
| GET | 查询列表、详情、导出任务状态 |
| POST | 新增、提交、登录、业务动作 |
| PUT | 全量更新或明确保存 |
| PATCH | 部分更新、状态局部变更 |
| DELETE | 删除或作废，核心业务建议使用 POST 动作替代 |

### 4.3 统一响应规范

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": "2026-05-21 10:00:00",
  "traceId": "9f7c2a..."
}
```

分页响应规范：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "records": [],
    "total": 100,
    "pageNum": 1,
    "pageSize": 20,
    "pages": 5
  }
}
```

### 4.4 错误码规范

| 范围 | 类型 | 示例 |
|---|---|---|
| 200 | 成功 | 200 操作成功 |
| 400xx | 请求错误 | 40001 参数错误、40002 数据不存在 |
| 401xx | 认证错误 | 40101 未登录、40102 令牌过期 |
| 403xx | 授权错误 | 40301 无权限、40302 数据越权 |
| 409xx | 冲突错误 | 40901 状态不允许、40902 重复提交 |
| 500xx | 系统错误 | 50001 系统异常、50002 外部系统异常 |

### 4.5 参数校验规范

| 场景 | 规则 |
|---|---|
| 新增 | 必填字段使用 `@NotNull`、`@NotBlank`、`@NotEmpty` |
| 更新 | ID 必填，版本号建议必填用于乐观锁 |
| 金额数量 | 使用 `@DecimalMin`、`@Digits` 校验 |
| 枚举 | 使用自定义枚举校验，禁止接收未知状态 |
| 时间范围 | 开始时间不得大于结束时间 |
| 列表大小 | 批量接口限制最大条数 |

### 4.6 幂等规范

以下接口必须具备幂等能力：

| 接口类型 | 幂等方式 |
|---|---|
| 外部系统推送 | 外部单号 + 事件类型唯一约束 |
| 支付或付款回传 | 回执号唯一约束 |
| 消息消费 | 消息 ID 消费记录表 |
| 表单重复提交 | 幂等 Token 或业务唯一键 |
| 导入任务 | 文件摘要 + 任务类型唯一判断 |

## 5. 后端编码规范

### 5.1 包结构规范

业务模块建议使用以下结构：

```text
com.supplier.{module}/
├── controller
├── service
├── service/impl
├── mapper
├── entity
├── dto
├── vo
├── query
├── enum
├── converter
└── event
```

### 5.2 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| Controller | 参数接收、校验、返回结果 | 写复杂业务逻辑 |
| Service | 事务边界、业务编排、状态流转 | 直接拼接 SQL |
| Mapper | 数据访问 | 写业务判断 |
| Entity | 数据库映射 | 暴露给前端作为响应对象 |
| DTO | 请求入参 | 承载数据库注解 |
| VO | 响应出参 | 参与数据库写入 |
| Converter | DTO、Entity、VO 转换 | 混入业务校验 |

### 5.3 事务规范

| 规则 | 说明 |
|---|---|
| 写操作加事务 | 新增、修改、删除、状态流转必须具备事务边界 |
| 事务放 Service | 事务注解放在 public Service 方法上 |
| 避免大事务 | 文件上传、外部接口调用、消息发送不应放入长事务 |
| 先落库后发消息 | 本地事务成功后发布事件，可使用事务消息或 outbox 表 |
| 异常回滚 | 业务异常与运行时异常需明确回滚策略 |

### 5.4 状态机规范

所有核心单据必须定义允许状态迁移表。以采购订单为例：

| 当前状态 | 允许动作 | 目标状态 |
|---|---|---|
| 待下发 | 下发 | 待确认 |
| 待确认 | 接单 | 已确认 |
| 待确认 | 拒单 | 已拒单 |
| 已确认 | 创建 ASN | 部分发货 |
| 部分发货 | 全部收货 | 已完成 |
| 待下发、待确认、已确认 | 取消 | 已取消 |

实现要求：

| 规则 | 说明 |
|---|---|
| 入口统一 | 状态变更必须走专用 Service 方法 |
| 校验前置 | 变更前校验当前状态与用户权限 |
| 轨迹记录 | 每次状态变更写入轨迹表 |
| 并发控制 | 使用乐观锁或行锁防止重复变更 |

### 5.5 异常处理规范

| 异常类型 | 处理方式 |
|---|---|
| 参数校验异常 | 返回 40001 与字段错误详情 |
| 业务异常 | 返回业务错误码与明确提示 |
| 认证异常 | 返回 401xx |
| 授权异常 | 返回 403xx |
| 外部系统异常 | 返回 50002，并记录接口日志 |
| 未知异常 | 返回通用系统异常，不向前端暴露堆栈 |

### 5.6 日志规范

| 日志类型 | 内容 |
|---|---|
| 请求日志 | traceId、用户、IP、方法、路径、耗时、状态码 |
| 业务日志 | 单据号、动作、前状态、后状态、操作人 |
| 错误日志 | traceId、异常类型、堆栈、关键上下文 |
| 集成日志 | 请求地址、请求摘要、响应摘要、耗时、重试次数 |
| 安全日志 | 登录成功失败、越权访问、敏感操作、导出行为 |

日志禁止输出密码、JWT、银行卡完整号、密钥、完整身份证号等敏感信息。

## 6. 前端编码规范

### 6.1 Vue 组件规范

| 规则 | 说明 |
|---|---|
| 使用 Composition API | 统一使用 `<script setup>` 风格 |
| 组件命名 | PascalCase，例如 `OrderDetailPanel.vue` |
| 页面命名 | 与业务路由一致，例如 `PurchaseOrderList.vue` |
| API 分离 | 页面不直接写请求 URL，统一放入 `api` 目录 |
| 状态管理 | 用户信息、权限、字典、全局配置放入 Pinia |
| 表单校验 | 前端校验提升体验，后端校验保证安全 |

### 6.2 页面交互规范

| 场景 | 规则 |
|---|---|
| 列表页 | 查询区、操作区、表格区、分页区布局统一 |
| 详情页 | 单据头、明细、附件、操作日志、审批记录分区展示 |
| 弹窗 | 简单编辑可弹窗，复杂单据使用独立页面 |
| 删除 | 必须二次确认，核心单据使用作废而非删除 |
| 导出 | 大数据量导出使用异步任务 |
| 权限 | 菜单、按钮、路由均根据权限控制 |

### 6.3 字典与枚举规范

前端展示状态、类型、等级、处理方式等字段时，优先使用后端字典接口或统一枚举文件。禁止在多个页面重复写死同一组状态文案。

## 7. 安全规范

### 7.1 认证规范

| 规则 | 说明 |
|---|---|
| JWT 传输 | 使用 `Authorization: Bearer {token}` |
| 登录失败限制 | 连续失败应触发验证码、锁定或限流 |
| Token 过期 | 访问令牌短有效期，刷新令牌长有效期 |
| 登出处理 | 服务端记录令牌黑名单或变更 token version |
| 密码存储 | 使用 BCrypt 等不可逆哈希，禁止明文或可逆加密 |

### 7.2 授权规范

| 规则 | 说明 |
|---|---|
| 最小权限 | 新角色默认无权限，按需授权 |
| 后端强校验 | 接口必须校验功能权限与数据权限 |
| 供应商隔离 | 供应商用户只能访问自身 `supplier_id` 数据 |
| 敏感字段脱敏 | 银行账号、税号、联系人手机号按场景脱敏 |
| 导出权限 | 导出、下载、批量操作单独授权 |

### 7.3 输入与文件安全

| 场景 | 规则 |
|---|---|
| SQL 注入 | 使用 MyBatis 参数绑定，禁止字符串拼接 SQL |
| XSS | 富文本与用户输入展示前过滤或转义 |
| 文件上传 | 限制大小、类型、扩展名、MIME，生成随机存储名 |
| 文件下载 | 校验业务权限，不暴露真实磁盘路径 |
| 外部 URL | 回调地址、重定向地址必须白名单校验 |

## 8. 消息事件规范

### 8.1 事件命名

事件名使用 `{domain}.{entity}.{action}` 格式。

| 事件 | 说明 |
|---|---|
| `order.purchase.created` | 采购订单创建 |
| `order.purchase.confirmed` | 采购订单确认 |
| `delivery.asn.created` | ASN 创建 |
| `quality.ncr.created` | NCR 创建 |
| `settlement.reconciliation.confirmed` | 对账确认 |

### 8.2 事件消息结构

```json
{
  "eventId": "uuid",
  "eventType": "order.purchase.created",
  "occurredAt": "2026-05-21 10:00:00",
  "source": "supplier-collaboration",
  "traceId": "trace-id",
  "data": {
    "businessId": 1,
    "businessNo": "PO202605210001"
  }
}
```

### 8.3 消费规范

| 规则 | 说明 |
|---|---|
| 幂等消费 | 使用 `eventId` 或业务唯一键去重 |
| 失败重试 | 短暂异常自动重试，超过次数进入死信队列 |
| 人工补偿 | 死信消息必须可查询、重放、忽略 |
| 顺序要求 | 同一业务单据需要顺序时按业务 ID 分区或加锁 |
| 可观测 | 消费耗时、失败次数、堆积数量纳入监控 |

## 9. 文件存储规范

### 9.1 存储路径规范

对象存储路径建议采用：

```text
{bucket}/{module}/{yyyy}/{MM}/{dd}/{businessNo}/{uuid}.{ext}
```

示例：

```text
supplier-quality/quality/2026/05/21/NCR202605210001/7f3a9c.pdf
```

### 9.2 文件元数据规范

文件上传后应在业务表或附件表中保存：

| 字段 | 说明 |
|---|---|
| `file_name` | 原始文件名 |
| `file_ext` | 文件扩展名 |
| `file_size` | 文件大小 |
| `content_type` | MIME 类型 |
| `bucket_name` | 存储桶 |
| `object_key` | 对象 Key |
| `file_hash` | 文件摘要，用于去重和完整性校验 |
| `business_type` | 业务类型 |
| `business_id` | 业务 ID |

## 10. 缓存规范

| 场景 | 规则 |
|---|---|
| 字典缓存 | 字典修改后主动删除缓存 |
| 权限缓存 | 用户角色权限变更后清理对应用户缓存 |
| 热点列表 | 允许短 TTL 缓存，避免缓存与数据库长期不一致 |
| 分布式锁 | 必须设置过期时间，释放锁校验持有者 |
| 缓存穿透 | 空值短 TTL 缓存或布隆过滤器 |
| 缓存击穿 | 热点 key 加互斥锁或逻辑过期 |

## 11. 运维部署规范

### 11.1 配置规范

| 规则 | 说明 |
|---|---|
| 环境隔离 | dev、test、uat、prod 使用不同配置 |
| 敏感配置 | 密码、密钥、访问令牌不得提交到代码库 |
| 默认密码 | 生产环境必须修改 Docker 默认账号密码 |
| 配置命名 | 使用清晰前缀，例如 `spring.datasource`、`jwt.secret` |
| 配置审计 | 生产配置变更需记录变更人、时间、原因 |

### 11.2 发布规范

| 阶段 | 要求 |
|---|---|
| 构建 | 后端 Maven 构建，前端 Vite 构建，产物版本号明确 |
| 测试 | 单元测试、接口测试、关键流程冒烟测试通过 |
| 数据库 | DDL/DML 变更先备份，后执行，最后验证 |
| 发布 | 支持滚动、蓝绿或灰度发布 |
| 回滚 | 应用镜像、配置、数据库变更均需回滚预案 |

### 11.3 备份规范

| 组件 | 备份内容 | 建议 |
|---|---|---|
| MySQL | 全量备份、Binlog | 每日全量 + 实时 Binlog |
| Redis | RDB、AOF | 根据重要性开启 AOF |
| MongoDB | dump 或快照 | 每日备份 |
| MinIO | 对象数据与桶策略 | 定期同步到备份存储 |
| Elasticsearch | Snapshot | 定期快照，索引可重建但快照能加速恢复 |

## 12. 测试规范

### 12.1 测试分层

| 类型 | 覆盖内容 |
|---|---|
| 单元测试 | 工具类、状态机、金额计算、权限判断 |
| 集成测试 | Mapper、Service、消息消费、外部接口适配 |
| API 测试 | 登录、订单、ASN、质检、对账等接口 |
| 前端测试 | 表单校验、权限按钮、关键页面渲染 |
| 冒烟测试 | 登录、接单、发货、收货、质检、对账主链路 |
| 安全测试 | 越权、SQL 注入、XSS、文件上传绕过 |

### 12.2 关键验收场景

| 模块 | 场景 |
|---|---|
| 登录权限 | 内部用户与供应商用户登录后菜单、数据范围正确 |
| 供应商准入 | 资质过期、重复信用代码、黑名单供应商无法通过 |
| 订单协同 | 供应商只能接收自身订单，重复接单不会产生异常状态 |
| ASN | 超订单数量发货被拦截，收货差异可追溯 |
| 质量 | 不合格记录能生成 NCR，并通知供应商整改 |
| 对账 | 对账金额与收货、退货、扣款一致 |
| 导出 | 无导出权限无法导出，导出日志可追溯 |

## 13. 代码提交与分支规范

### 13.1 分支规范

| 分支 | 用途 |
|---|---|
| `master` | 生产稳定分支 |
| `develop` | 开发集成分支 |
| `feature/*` | 功能开发 |
| `hotfix/*` | 生产紧急修复 |

### 13.2 提交规范

提交信息遵循 Conventional Commits：

| 类型 | 说明 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |

| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建、依赖、配置等杂项 |

示例：

```text
feat(order): add purchase order confirmation flow
fix(security): prevent supplier data scope bypass
docs(database): add table design rules
```
